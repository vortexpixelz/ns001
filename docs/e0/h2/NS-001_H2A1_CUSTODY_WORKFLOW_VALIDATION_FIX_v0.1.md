## Duplicate-key correction

Both API JSON and provenance JSON now use one `object_pairs_hook` parser that
rejects a repeated decoded key before returning an object. The hook applies at
every object nesting level, including objects inside arrays. Equal duplicate values
also fail; escaped spellings resolving to the same key fail. Unique key/value
semantics, including nested values, remain unchanged. There is no last-value-wins
fallback. Other JSON behavior is not redesigned in this two-defect correction.

The hook raises `SystemExit`, stopping the shell step before the attestation action.
No trigger, job condition, permission, action pin, file pin or signing subject changes.

## Timestamp correction and exact field inventory

The existing custom predicate carries two required service publication timestamps:

| Source field | Existing predicate field | Correction |
| --- | --- | --- |
| `release.published_at` | `release_published_at` | Validate before tag resolution and signing. |
| H1 ZIP `asset.created_at` | `asset_created_at` | Validate after exact ZIP download and before signing. |

The provenance JSON contract has no required timestamp field; the provenance asset's
creation time is not carried in this predicate. Neither is newly mandated here.
`observed_at` is generated by the runner and remains separate from service timestamps;
no change is made to its representation or interpretation.

Validation requires a string exactly in `YYYY-MM-DDTHH:MM:SSZ` form, then validates
calendar/time components with `datetime.strptime`. Null, absent, empty, nonstring,
malformed or impossible dates/times fail. No whitespace stripping, coercion,
clock substitution, time-ordering rule, age restriction, or historical assertion
is introduced. Non-UTC offsets and fractional precision are rejected for these
service fields because the intended GitHub REST response format is UTC with a
trailing Z and second precision.
[GitHub REST response format](https://docs.github.com/en/rest/using-the-rest-api/getting-started-with-the-rest-api#about-the-response-body).
These values remain service-reported observations, not cryptographically verified
historical timestamps. Missing values are checked via `.get` and fail explicitly.
